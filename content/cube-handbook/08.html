    Access Control

    Ai được gọi Cube, và gọi rồi thì thấy được dữ liệu nào: xác thực, security context, access policy, data masking và multitenancy.

    Trần Ngọc Đăng KhôiChương 08 / 0822 phút đọc
    Mục lục chương
      Ý chính của chươngMặc định mọi thứ trong data model đều public. Kiểm soát truy cập là thu hẹp dần phạm vi đó: JWT cho biết người gọi là ai, access policy quyết định họ thấy cột nào, dòng nào và giá trị nào bị che, còn queryRewrite giữ những luật chung cho cả hệ thống.
      08.1

      Bức tranh tổng thể

      Xác thực quyết định ai được vào Cube. Phân quyền quyết định người đó thấy dữ liệu nào.

      Data model là lớp mặt tiền đặt trước data warehouse. Mặc định mọi cube, view và member đều public, mọi dòng đều trả về. Mỗi request đi qua một chuỗi hook, hook nào cũng đọc securityContext. Docs của Cube khuyên dùng access policy làm cách phân quyền chính, còn query_rewrite dành cho trường hợp nâng cao. Chọn từng bước để xem hook nào chạy và cấu hình ở đâu.

      08.2

      Xác thực

      Cube kiểm tra chữ ký JWT rồi lấy payload làm securityContext.

      Cube xác minh JWT bằng secret chung (CUBEJS_API_SECRET) hoặc bằng JWKS (CUBEJS_JWK_URL), có thể kiểm thêm audience, issuer và subject. Token nên có exp để giới hạn thời hạn. Sửa payload bên trái để xem Cube xử lý ra sao.

      Ghi nhớDev mode (CUBEJS_DEV_MODE=true) bỏ qua yêu cầu token và cho Playground tự ký token với securityContext tùy ý. Chỉ bật trên máy cá nhân, không bật trên production.
      Đọc sâuCấu hình JWT, check_auth và SQL API

      Khi dùng identity provider, khai báo JWKS và các trường cần kiểm. Cube cache JWKS và tải lại khi có key rotation (khóa ký được thay mới).

      module.exports = {
  jwt: {
    jwkUrl: "<URL_TO_JWKS_JSON>",
    audience: "<AUDIENCE_FROM_IDENTITY_PROVIDER>",
    issuer: ["<ISSUER_FROM_IDENTITY_PROVIDER>"],
    subject: "<SUBJECT_FROM_IDENTITY_PROVIDER>",
    claimsNamespace: "my-custom-namespace"
  }
}

      Muốn tự viết logic xác minh thì dùng check_auth: hàm kiểm token và trả về securityContext. SQL API không dùng JWT mà đăng nhập bằng user và password qua checkSqlAuth:

      module.exports = {
  checkSqlAuth: async (req, username) => {
    if (username === "fooUser") {
      return { password: "mypassword", securityContext: {} }
    }
    throw new Error("Incorrect user name or password")
  }
}

      User khai báo trong CUBEJS_SQL_SUPER_USER được đổi securityContext cho từng truy vấn bằng bộ lọc ảo WHERE __user = 'anotheruser'. Quy tắc chi tiết hơn đặt trong canSwitchSqlUser.

      08.3

      Security context

      Một object chứa các claim đã xác minh; mọi quy tắc truy cập đều đọc từ đây.

      securityContext phải là object, thường lồng nhau (ví dụ user_id, location.country). Key cubeCloud dành riêng cho tính năng của Cube Cloud, không dùng vào việc khác. securityContext có mặt trong query_rewrite, extend_context và trong data model qua COMPILE_CONTEXT.securityContext.

      extend_context bổ sung trường mới trước khi Cube đánh giá các quy tắc truy cập. Data model dùng tiếp được trường suy ra này:

      cube.jsJavaScript
      module.exports = {
  extendContext: ({ securityContext }) => ({
    securityContext: {
      ...securityContext,
      isFinance: securityContext.department === 'finance'
    }
  })
};
      model/views/finance_view.ymlYAML
      views:
  - name: finance_view
    public: {{ COMPILE_CONTEXT['securityContext']['isFinance'] }}

      Cube Cloud và Cube Core lấy group và thuộc tính người dùng từ hai nguồn khác nhau:

      Cube CoreGroup do hàm context_to_groups trả về từ securityContext. Trong policy, giá trị theo người dùng viết là "{ securityContext.country }".
      Cube CloudGroup và user attributes quản lý trong tài khoản Cube Cloud. Trong policy viết "{ userAttributes.country }". Gọi Core Data API trực tiếp thì đặt chúng trong JWT dưới key cubeCloud: {"cubeCloud": {"groups": [...], "userAttributes": {...}}}.

      Khi phát triển, Developer Playground cho nhập JWT hoặc dựng token từ một object JSON, nên có thể thử quy tắc truy cập với từng securityContext.

      08.4

      Member-level security

      member_level quyết định group nào được truy vấn member nào.

      Trong mỗi policy, member_level nhận includes (danh sách được phép) hoặc excludes (danh sách bị cấm); "*" nghĩa là mọi member. Khi đã khai báo policy cho một số group, các group còn lại tự động bị từ chối, không cần policy chặn riêng.

      model/views/orders_view.ymlYAML
      access_policy:
  # Managers can access all members except for `count`
  - group: manager
    member_level:
      excludes: [count]
  # Observers can access all members except for `count` and `count_7d`
  - group: observer
    member_level:
      excludes: [count, count_7d]
  # Guests can only access the `count_30d` measure
  - group: guest
    member_level:
      includes: [count_30d]

      Access policy cũng tính tới tham số public trên cube, view và member: member phải vừa public vừa được policy cho phép. Khi truy vấn qua view, Cube chỉ áp member_level khai báo trên view và bỏ qua member_level trên các cube bên dưới. Docs cũng ghi rằng policy thường được đặt trên view.

      08.5

      Row-level security

      row_level thêm bộ lọc dòng, giá trị lấy từ securityContext của người gọi.

      Mặc định không có bộ lọc nào, mọi dòng đều public. row_level.filters gồm các bộ lọc có member, operator, values; có thể kết hợp nhiều bộ lọc bằng and và or. Giá trị theo người dùng viết dạng template:

      model/cubes/orders.ymlYAML
      cubes:
  - name: orders
    access_policy:
      - group: manager
        row_level:
          filters:
            - member: country
              operator: equals
              values: [ "{ securityContext.country }" ]

      Trong ví dụ trên, manager chỉ thấy đơn của nước mình. Mọi group khác không thấy dòng nào, vì không có policy nào cho họ. Bản JavaScript viết trực tiếp values: [ securityContext.country ]. Row-level cũng làm được bằng query_rewrite (mục 08.8); khi có cả hai, Cube áp cả hai bộ lọc.

      08.6

      Gộp nhiều policy

      Member gộp theo OR giữa các policy; dòng phải được phép với mọi member trong truy vấn.

      Một user có thể thuộc nhiều group nên khớp nhiều policy. Hãy hình dung quyền như một lưới: cột là member, hàng là dòng dữ liệu, mỗi policy phủ một hình chữ nhật trên lưới. Cube gộp các hình chữ nhật theo hai quy tắc. Member được truy vấn nếu bất kỳ policy nào cho phép. Dòng chỉ được trả về khi được phép với mọi member có trong truy vấn.

      model/views/orders_view.ymlYAML
      access_policy:
  - group: support
    member_level:
      includes: [status, count]
    row_level:
      filters:
        - member: region
          operator: equals
          values: [US]
  - group: finance
    member_level:
      includes: [count, revenue]
    row_level:
      filters:
        - member: region
          operator: equals
          values: [EU]

      Với một user thuộc cả hai group, bốn truy vấn sau cho kết quả khác nhau:

      Member truy vấnDòng trả vềLý do
      status, countUSchỉ support cho phép status
      count, revenueEUchỉ finance cho phép revenue
      countUS + EUcả hai policy cho phép count, gộp hai bộ lọc
      status, count, revenuerỗngUS ∩ EU không có dòng nào
      Ghi nhớAccess policy mặc định từ chối: member không được policy nào cho phép thì truy vấn trả về rỗng. Docs chỉ ghi “an empty result”, không nói Cube có báo lỗi kèm theo hay không.
      08.7

      Data masking

      Thay vì chặn member, trả về giá trị đã che.

      Member nằm trong member_level trả giá trị thật. Member chỉ nằm trong member_masking trả giá trị che. Member không nằm trong danh sách nào thì bị từ chối. Cube Core hỗ trợ masking từ v1.6.23.

      Giá trị che lấy từ tham số mask của member: số tĩnh như -1, hoặc biểu thức SQL. Không khai báo mask thì giá trị che là NULL. Muốn đổi mặc định theo kiểu dữ liệu, đặt các biến CUBEJS_ACCESS_POLICY_MASK_STRING, _NUMBER, _BOOLEAN, _TIME.

      model/cubes/customers.ymlYAML
      dimensions:
  - name: email
    sql: email
    type: string
    mask:
      sql: "CONCAT(LEFT({CUBE}.email, 2), '***')"
  - name: revenue
    sql: revenue
    type: number
    mask: -1
access_policy:
  - group: support
    member_level:
      includes: [name, region]
    member_masking:
      includes: "*"
  - group: finance_eu
    member_level:
      includes: "*"
    row_level:
      filters:
        - member: region
          operator: equals
          values: [EU]
  - group: finance
    member_level:
      includes: "*"
      Đọc sâuGiới hạn của masking

      Cube không áp mask SQL trên measure cho truy vấn ungrouped (không có GROUP BY), ví dụ SELECT * qua SQL API. Mask tĩnh như mask: -1, mask: 0 thì luôn được áp. Muốn che động một measure trong truy vấn ungrouped, tạo dimension có mask SQL rồi truy vấn dimension đó.

      Với measure, masking có điều kiện chỉ chạy khi truy vấn group theo các member dùng trong bộ lọc dòng. Nếu không, cả measure trả về giá trị che (mặc định NULL).

      08.8

      queryRewrite

      Hàm chạy ở mọi request, sửa query hoặc chặn hẳn truy vấn.

      Cube gọi queryRewrite ở mọi request, ngay trước khi biên dịch truy vấn. Hàm nhận query dạng JSON (measures, dimensions, filters) cùng securityContext rồi trả về query mới. Trong hàm có thể thêm bộ lọc, sửa query, hoặc ném lỗi để chặn truy vấn. Hàm trả query nguyên vẹn thì truy vấn vẫn chạy, nên mặc định của queryRewrite là cho qua.

      cube.jsJavaScript
      module.exports = {
  queryRewrite: (query, { securityContext }) => {
    // thiếu role thì chặn truy vấn
    if (!securityContext.role) throw new Error('Thiếu role trong securityContext');
    // bộ lọc bắt buộc cho mọi truy vấn
    query.filters.push({
      member: 'orders.created_at',
      operator: 'afterDate',
      values: ['2019-12-30']
    });
    return query;
  }
};
      queryRewriteViết code trong cube.js, áp cho mọi cube. Chỉ lọc được dòng hoặc chặn cả truy vấn. Mặc định cho qua. Hợp với luật chung cho toàn hệ thống: cách ly tenant, bắt buộc có claim, chặn truy vấn bất thường.
      access_policyKhai báo trong YAML của từng cube hoặc view, theo group. Quy định cột (member), dòng (row) và giá trị bị che (masking). Group không có policy thì bị từ chối. Hợp với phân quyền theo vai trò.
      Dùng cùng nhauqueryRewrite giữ ranh giới tenant và từ chối token thiếu thông tin. Access policy chia quyền giữa các vai trò trong một tenant. Bộ lọc của cả hai đều nằm trong SQL gửi tới data warehouse.
      08.9

      Multitenancy

      Mỗi tùy chọn cấu hình tách thêm một lớp tài nguyên cho từng tenant.

      Cách đơn giản nhất là mọi tenant dùng chung database và queryRewrite lọc theo tenant_id. Khi tenant cần model, bảng hoặc database riêng, thêm dần các tùy chọn bên dưới. Mỗi ID riêng tốn từ vài MB đến vài chục MB bộ nhớ, nên với nhiều tenant cần gom tenant vào ít ID hoặc chia ra nhiều node Cube.

      Ghi nhớMultitenancy khác nhiều data source. Một data model đọc từ nhiều nguồn thì dùng thuộc tính data_source của cube; các tenant không liên quan, cần bộ dữ liệu khác nhau, mới dùng các tùy chọn multitenancy.
      08.10

      Case study: SaaS bán lẻ

      queryRewrite giữ ranh giới tenant, access policy chia quyền theo vai trò.

      Một công ty SaaS nhúng dashboard bán hàng cho nhiều chuỗi bán lẻ, mỗi chuỗi là một tenant. Trong một chuỗi có ba vai trò. Nhân viên cửa hàng chỉ xem đơn của cửa hàng mình và không thấy doanh thu. Quản lý vùng xem đủ số liệu của vùng mình, nhưng email khách hàng bị che. Phòng tài chính xem toàn bộ dữ liệu của chuỗi. Backend của công ty ký JWT cho từng người dùng, trong đó có các claim tenant_id, roles, store_id, region.

      cube.jsJavaScript
      module.exports = {
  // roles trong JWT trở thành group cho access policy
  contextToGroups: ({ securityContext }) => securityContext.roles || [],

  // luật chung: không có tenant_id thì chặn, có thì khóa vào tenant đó
  queryRewrite: (query, { securityContext }) => {
    if (!securityContext.tenant_id) throw new Error('Token thiếu tenant_id');
    query.filters.push({
      member: 'orders_view.tenant_id',
      operator: 'equals',
      values: [securityContext.tenant_id]
    });
    return query;
  }
};
      model/views/orders_view.yml (phần access_policy)YAML
      access_policy:
  - group: store_staff
    member_level:
      includes: [status, created_at, count]
    row_level:
      filters:
        - member: store_id
          operator: equals
          values: ["{ securityContext.store_id }"]
  - group: manager
    member_level:
      excludes: [customer_email]
    member_masking:
      includes: [customer_email]
    row_level:
      filters:
        - member: region
          operator: equals
          values: ["{ securityContext.region }"]
  - group: finance
    member_level:
      includes: "*"
      Ghi nhớLuật “ai thuộc tenant nào” đặt ở queryRewrite, vì queryRewrite áp cho mọi cube và chặn được token thiếu claim. Luật “vai trò nào xem cột nào, dòng nào” đặt ở access policy, vì policy nằm cạnh model, dễ đọc và mặc định từ chối.
